# Trash and restore

Move a file or populated folder to Trash, then use **Restore** to return it to its original parent and name. A missing or hidden parent, or a name conflict, blocks restoration. Restore the parent first or rename the conflicting active item. Account roots cannot be moved to Trash. When a selection contains a folder and an item inside it, the folder action covers both.

`GET /trash` accepts `limit` (1–200, default 100) and `cursor`. Responses contain `items`, `next_cursor` and `has_more`, ordered by original name then entry ID. Signed cursors belong to the account and its namespace state. Invalid cursors return `400 invalid_cursor`; any account namespace change returns `409 listing_changed`, so restart from page one. Other accounts' changes do not invalidate the cursor. Returned rows include `needs_reference: true` when another deleted item has the same name and full displayed original path, including duplicates on other pages and under different historical parent IDs. The server streams same-name peers and checks one ancestry at a time; it does not retain the complete Trash inventory or its paths.

A folder operation is one atomic metadata transaction. Only the selected root becomes deleted; active descendants remain stored behind it. Files, search, direct content requests and mutations require an active same-owner path to the private root. Restoring the folder makes its active tree reachable again, with the same structure, revisions and bytes. Earlier deletions stay separate in Trash and cannot be restored through a hidden ancestor.

Trashing increments generations on the selected root, its active reachable descendants and its original parent. Traversal stops at earlier deletions. Restoring increments the selected root and its parent. Old descendant etags, listing cursors and upload parent preconditions stay stale after a trash/restore cycle. Writer order determines which moves and upload commits finish before the tree is hidden; later effects fail their current ancestry or generation check. Existing upload admission replay, status, cancellation and reconciliation remain available.

Namespace operations have no durable operation ID. After a network failure or server error, the outcome is unconfirmed. Inspect fresh Files and Trash before acting again. Inspection can establish current state, but does not prove that a particular request ran exactly once. If the original parent is unavailable, inspect Trash and dismiss the unconfirmed result to recover the parent before checking the item again. Never automatically retry a trash or restore effect after an unknown reply.

Select Trash items and choose **Remove permanently**, or choose **Empty Trash**. The confirmation names the item count and states that removal cannot be undone. The count covers Trash roots; a selected folder also removes its active descendants. Earlier deleted descendants remain separate unless selected or included by Empty Trash. Historical paths and immutable upload results remain stored.

`POST /trash/removals/preview` accepts `{"selection":{"kind":"selected","items":[{"id":"…","etag":"…"}]}}` (up to 200 items) or `{"selection":{"kind":"all"}}`. It returns `confirmation` and `count`. The signed confirmation belongs to the account and removal snapshot (selected roots, their active descendants and ancestry; all deleted roots for Empty Trash) and expires after ten minutes. `POST /trash/removals` accepts `operation_id` (32 lowercase hexadecimal characters) and that confirmation. Changes to that effect or count return `409 listing_changed`; obtain a fresh preview and confirmation. Unrelated uploads and sibling changes do not invalidate the confirmation. A stale selected item or empty Trash returns `404 not_found` at preview; refresh before choosing again. Preview and execution require the current session, Origin and CSRF token.

Removal atomically records its immutable result, members and payload cleanup authorization. Removed entries cannot be restored or served. Revisions remain as metadata. Bytes shared by any retained revision, including another account, remain available. Authorized unreferenced payloads are reserved against new revision references before unlink; directory synchronization precedes cleanup completion. Serving retries authorized cleanup in bounded background passes, with filesystem work off the async executor. Failures emit only `removal.cleanup_pending` with a fixed redacted reason. The server joins cleanup before closing SQLite or releasing root ownership. Startup resumes interrupted authorized cleanup before readiness; an unlink or sync failure still refuses readiness under the existing fail-closed recovery policy. It never sweeps unrelated files.

A successful removal returns `state: "committed"`, `count` and `cleanup: "pending"` or `"complete"`. Cleanup failure does not undo committed removal or block other Trash actions. The browser retains the original operation and confirmation in account-scoped session storage before submitting, so recovery survives reload and signing back into the same account. Use **Retry same removal** deliberately when status stays unknown; it sends the exact original request. A stale or expired uncommitted confirmation is rejected, after which a fresh preview is required. No new removal is sent automatically. If browser storage is unavailable, keep the tab open until the outcome resolves. After a lost response, use authenticated `GET /trash/removals/{operation_id}` or resubmit the exact original operation and confirmation. An unknown operation remains unresolved; do not create another removal to infer success. Exact replay reads the durable result even after confirmation expiry. Other accounts receive `state: "unknown"` on both status and replay. Reusing a committed operation with a different confirmation returns `409 operation_conflict`. A definite transaction rollback returns `409 removal_not_committed`; server errors with uncertain outcomes still require reconciliation.

Removal uses the same coordinator admission gate as namespace mutations. The SQLite writer serializes removal against upload publication and namespace effects; session, CSRF and snapshot checks run in that same writer transaction. Roots resolve before result insertion, and any later domain or SQL failure rolls the transaction back. Retained-reference triggers prevent a publication ordered after cleanup reservation from attaching a deleting blob.

## Schema upgrade and offline admin

Startup upgrades a schema v1 root through v2 to the current schema v3. The database transaction records the exact previous binding before atomically replacing the manifest. If interrupted between those writes, startup resumes only the recorded identity transition. Other mismatches still refuse startup. Functional checks do not qualify physical durability, upgrades on every deployment, secure erasure or deployment readiness. There is no automatic expiry or revision pruning.

The schema change is one-way. Take a complete stopped-service backup with the
previous release before upgrading. Rollback requires restoring that whole backup
with its matching release. Do not pair an old binary or manifest with newer metadata.
Offline payload verification and password recovery do not migrate a root. They
report `*_schema_upgrade_required_run_serve` for a v1 or v2 manifest, including an
interrupted upgrade. Run the new release's `serve` with the same root to complete
the recorded transition, then stop it before using the offline admin command.
Do not hand-edit versions or identity fields to bypass a refusal.
